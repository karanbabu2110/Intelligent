Technical functionality maps

Read these four connected views in order. Green arrows are calls or writes toward a dependency, blue arrows are returned data or control, and magenta dashed arrows are failures. Arrow direction follows the actual call or return direction.

1. Command routing

This view answers: “Which code handles my command, and where does that branch finish?” Only one command branch is selected for each invocation. The two AI branches continue into view 2; knowledge ingestion continues into view 4.

2. AI streaming sequence

This view answers: “What crosses the Ollama boundary, what repeats while streaming, and what returns once?” Green moves toward Ollama; blue moves back to KAOS and the user.

3. Conversation state

This view answers: “What is restored before input, what is written after a clean result, and where does control return?” A clean prompt uses view 2. Green arrows point into calls and writes; blue arrows carry restored data, commits, or loop control back; magenta dashed arrows carry failures from the boundary that detected them.

5. Local knowledge preparation flow

The knowledge command loads one explicit embedding model, then sends each exact chunk in order to fixed loopback POST /api/embed with truncate: false. The client validates the echoed model, one finite vector of 1–4,096 dimensions, consistent dimensions across chunks, a 128 KiB per-response limit, and one shared five-minute foreground deadline.

Architecture status

Implemented

Minimal application shell

One root project, entry point, validated local configuration, command routing, safe errors, logging, tests, packaging, and local verification.

Implemented

Local Ollama reachability

Feature 002.01 adds one bounded version request through an in-process package. It sends no prompt, model, secret, or file content.

Implemented

AI model configuration

Feature 002.02 resolves one explicit model, a 2K-64K context window, off/on thinking, and a 64-4,096 generated-token bound. Every prompt sends num_ctx, think, and num_predict; ordinary requests default to 512 tokens and reasoning to 2,048.

Implemented

Prompt submission

Feature 002.03 supplies the bounded prompt, model, and safe local request boundary that Feature 002.04 now streams. Prompts and raw failures are excluded from error output.

Implemented

Response streaming

Task 002.04.01 streams bounded answer chunks. Task 002.04.02 adds content-free thinking progress and answer isolation. Task 002.04.03 adds backpressure, total and inactivity deadlines, interruption cancellation, distinct local limits, and partial-output guidance without exposing prompts, provider bodies, or reasoning.

Implemented

AI error and timeout handling

Task 002.05.01 distinguishes unavailability before response acceptance, accepted-stream transport loss, total and inactivity timeouts, rejection, invalid data, limits, and cancellation. The application maps them to safe diagnostic families and actionable recovery without retaining prompt or provider details.

Implemented

AI integration testing

Task 002.06.01 crosses application routing, the real prompt client, ephemeral loopback HTTP, streamed NDJSON, and terminal output for success, unavailability, and partial malformed-stream safety. It runs in the standard JUnit lifecycle without Ollama, external network, a new source set, or production configuration.

Conversation domain model

Feature 003.01 adds conversation-owned immutable user and assistant messages with essential null/blank invariants and exact valid-content preservation.

Implemented

Message history

Task 003.02.01 adds caller-owned immutable history snapshots with defensive copying, ordered append, and unmodifiable exposure. Feature 003.02 was delivered by PR #28.

Implemented

Multi-turn AI context

The bounded Ollama chat client maps a supplied history in order, appends the current user prompt once, and decodes streamed assistant messages. Feature 003.03 was delivered by PR #29.

Implemented

Conversation creation and selection

One foreground command creates deterministic identifiers, switches isolated histories, sends selected context, and records only clean turns. Feature 003.04 introduced the session; Feature 004.05 now restores its newest bounded working set.

Implemented

Conversation limits and validation

One foreground session permits 8 conversations and 32 clean turns per conversation. Stored messages and immutable histories are bounded, and a full conversation rejects another prompt before Ollama submission without changing existing state. Feature 003.05 was delivered by PR #31.

Implemented

Conversation tests

The complete local path proves selected-conversation isolation, restored ordered history, streamed output, privacy-safe malformed-stream recovery, and exclusion of a failed partial turn from later context. Feature 003.06 was delivered by PR #32.

Selected decision

Local persistence selection

Feature 004.01 selected local SQLite as the authoritative store for conversations and ordered messages. It remains in process and supports transactional, targeted access beyond current in-memory limits.

Implemented component

SQLite conversation-record store

A concrete store persists stable identifiers transactionally, returns creation-ordered records capped at 1,000, and supplies only the newest bounded foreground working set at application startup.

Implemented component

Ordered SQLite message storage

Bounded user and assistant batches commit atomically. Exact validated roles and content return in insertion order after reopen, and tests prove 576 messages across nine conversations. Feature 004.03 was delivered by PR #35.

Implemented component

SQLite schema management

An empty database is initialized transactionally as version 1. Reopen validates columns, identifier uniqueness, the message foreign key, and the ordered-read index; conflicting and unsupported schemas fail safely.

Implemented runtime path

Conversation restore

The conversation command resolves a fixed local database filename, validates schema v1, restores its newest eight histories, continues identifiers above the durable maximum, and writes new identifiers plus complete clean turns.

Implemented failure boundary

Persistence failure handling

Schema and store failures become stable locked, corrupt, read-only, capacity, unavailable, invalid-state, or unknown reasons. The application gives phase-specific recovery, preserves rollback, and performs no automatic retry or repair.

Verified integration boundary

Persistence integration tests

Separate application runs use the real Ollama client, streamed loopback NDJSON, and one temporary SQLite database to prove exact clean-history restore and durable exclusion of failed partial turns.

Implemented admission boundary

Single text-document ingestion

One CLI path directly admits a regular non-link UTF-8 .txt file up to one MiB into an immutable foreground byte snapshot. Content remains transient; exact derived chunks now proceed to the explicit local embedding step.

Implemented extraction boundary

Text extraction

One direct in-process extractor converts the admitted bytes into exact bounded immutable Unicode text, preserves BOM, whitespace, and line endings, and reports only a code-point count to the CLI.

Implemented chunking boundary

Document chunking

One direct in-process chunker splits exact text into immutable ordered units of at most 1,000 Unicode code points with 200 code points of overlap. The CLI reports only the bounded chunk count.

Implemented embedding boundary

Embedding generation

Feature 005.04 turns every exact chunk into one ordered, finite, bounded vector through an explicitly selected local Ollama embedding model.

Implemented storage boundary

Vector storage

Feature 005.05 atomically stores exact chunks and vectors in version-1 local SQLite and restores bounded documents after restart.

Implemented retrieval boundary

Relevant-context retrieval

Feature 005.06 embeds one query, ranks same-model and same-dimension stored chunks, and returns the deterministic top three without printing content.

Implemented prompt boundary

Grounded prompt construction

Feature 005.07 places the exact question and whole ranked evidence records into one bounded injection-aware prompt. knowledge-retrieve constructs it; knowledge-ask submits it.

Implemented citation boundary

Source attribution

Feature 005.08 assigns stable labels to included prompt evidence and renders content-free source coordinates. knowledge-ask submits the prompt; answer-citation validation remains deferred.

Implemented evaluation evidence

RAG evaluation and testing

Feature 005.09 deterministically verifies the local knowledge pipeline from exact extraction through citation construction, including incompatible-model exclusion.

Feature 005.10

Grounded answer generation

knowledge-ask retrieves evidence, submits the exact grounded prompt with empty history, and streams the answer. Source coordinates follow clean completion; partial failures omit the manifest and retain the existing warning.

Feature 006.02 · implemented

Explicit memory creation

memory-create validates one fixed answer-detail key and three structured values, performs only the absent-to-present transition, and reports content-safe failures.

Feature 006.03 · implemented

Durable memory storage

A fixed local memory.db stores the preference through the existing SQLite JDBC driver. Versioned schema validation, a primary key, and content-free failures preserve create-only state across processes without a vector index.

Feature 006.04 · implemented

Bounded memory retrieval

AnswerDetailStore returns only absence or one validated enum. SQLite retrieval reads at most two rows and rejects unexpected keys, values, or additional state without exposing stored text.

Feature 006.05 · implemented

Memory use in AI context

One-shot ollama-prompt maps the optional enum to one fixed bounded system message before the unchanged user prompt. Absence preserves the prior request; conversation and knowledge submissions remain memory-free.

Feature 006.06 · implemented

Explicit memory inspection

memory-inspect answer-detail reuses exact validated retrieval and reports only absence or the structured enum. Invalid keys fail before database access, and inspection never mutates memory.

Feature 006.07 · implemented

Explicit memory editing and deletion

memory-edit atomically replaces a present structured value and memory-delete removes the present fixed row. Absence fails explicitly, and SQLite schema version 1 remains unchanged.

Boundary evolution ladder

PackageCurrent default: one capability package inside one application.
Gradle moduleOnly for measured dependency, build, test, or artifact isolation.
Library or repositoryOnly for real consumers and an independent release need.
Deployed serviceOnly for proven deployment, scale, fault, hardware, or security isolation.
