System architecture diagram

AI chat request flow diagram

This is the implemented Ollama chat flow. The conversation command admits a prompt only when its selected bounded history has room for one clean turn; ollama-prompt supplies empty history. Clean answers return to the selected in-memory history. The SQLite store is not invoked on this path, so it still has no runtime persistence, retry, worker, event bus, or remote provider.

Architecture status

Implemented

Minimal application shell

One root project, entry point, validated local configuration, command routing, safe errors, logging, tests, packaging, and local verification.

Implemented

Local Ollama reachability

Feature 002.01 adds one bounded version request through an in-process package. It sends no prompt, model, secret, or file content.

Implemented

AI model configuration

Feature 002.02 resolves one explicit model, a 2K-64K context window, off/on thinking, and a 64-4,096 generated-token bound. Every prompt sends num_ctx, think, and num_predict; ordinary requests default to 512 tokens and reasoning to 2,048.

Implemented

Prompt submission

Feature 002.03 supplies the bounded prompt, model, and safe local request boundary that Feature 002.04 now streams. Prompts and raw failures are excluded from error output.

Implemented

Response streaming

Task 002.04.01 streams bounded answer chunks. Task 002.04.02 adds content-free thinking progress and answer isolation. Task 002.04.03 adds backpressure, total and inactivity deadlines, interruption cancellation, distinct local limits, and partial-output guidance without exposing prompts, provider bodies, or reasoning.

Implemented

AI error and timeout handling

Task 002.05.01 distinguishes unavailability before response acceptance, accepted-stream transport loss, total and inactivity timeouts, rejection, invalid data, limits, and cancellation. The application maps them to safe diagnostic families and actionable recovery without retaining prompt or provider details.

Implemented

AI integration testing

Task 002.06.01 crosses application routing, the real prompt client, ephemeral loopback HTTP, streamed NDJSON, and terminal output for success, unavailability, and partial malformed-stream safety. It runs in the standard JUnit lifecycle without Ollama, external network, a new source set, or production configuration.

Verified

First end-to-end AI demonstration

Task 002.07.01 runs the packaged application through the existing fixed-loopback client and an explicitly selected installed model. One safe bounded prompt emitted its exact validated answer before clean completion, with exit 0 and empty error output.

Implemented

Conversation domain model

Feature 003.01 adds conversation-owned immutable user and assistant messages with essential null/blank invariants and exact valid-content preservation.

Implemented

Message history

Task 003.02.01 adds caller-owned immutable history snapshots with defensive copying, ordered append, and unmodifiable exposure. Feature 003.02 was delivered by PR #28.

Implemented

Multi-turn AI context

The bounded Ollama chat client maps a supplied history in order, appends the current user prompt once, and decodes streamed assistant messages. Feature 003.03 was delivered by PR #29.

Implemented

Conversation creation and selection

One foreground command creates deterministic process-local identifiers, switches isolated histories, sends the selected context, and records only clean turns. Every conversation is discarded when the process ends. Feature 003.04 was delivered by PR #30.

Implemented

Conversation limits and validation

One foreground session permits 8 conversations and 32 clean turns per conversation. Stored messages and immutable histories are bounded, and a full conversation rejects another prompt before Ollama submission without changing existing state. Feature 003.05 was delivered by PR #31.

Implemented

Conversation tests

The complete local path proves selected-conversation isolation, restored ordered history, streamed output, privacy-safe malformed-stream recovery, and exclusion of a failed partial turn from later context. Feature 003.06 was delivered by PR #32.

Selected decision

Local persistence selection

Feature 004.01 selected local SQLite as the authoritative store for conversations and ordered messages. It remains in process and supports transactional, targeted access beyond current in-memory limits.

New in Feature 004.02 Task 004.02.01
Implemented component

SQLite conversation-record store

A concrete store persists stable identifiers transactionally and returns an immutable creation-ordered list capped at 1,000. It requires caller-owned path and schema setup and is not connected to the foreground session.

Next roadmap checkpoint

Ordered message storage

Feature 004.03 owns durable user and assistant messages. It will extend the proven SQLite boundary after Feature 004.02 is reviewed and merged.

Not justified today

Distributed boundaries

No Gradle submodule, reusable library, separate repository, plugin, message bus, production database lifecycle, or microservice currently exists.
