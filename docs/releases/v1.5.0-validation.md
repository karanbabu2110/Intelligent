# KAOS 1.5.0 validation and publication checkpoint

## Outcome

`1.5.0` gives all verified work through completed Epic 007 one cumulative
release identity and adds the first explicitly approved, bounded local-file
tool path with deterministic end-to-end evidence.

## Reproducible validation

Run from the repository root with Java 21:

```powershell
./gradlew.bat properties --console=plain --no-daemon
./gradlew.bat clean verifyLocal --no-daemon --warning-mode=all
Get-ChildItem build/libs,build/distributions -File
Get-FileHash build/libs/KAOS-1.5.0.jar -Algorithm SHA256
Get-FileHash build/distributions/KAOS-1.5.0.tar -Algorithm SHA256
Get-FileHash build/distributions/KAOS-1.5.0.zip -Algorithm SHA256
git diff --check
```

Release preparation verifies:

- Gradle reports version `1.5.0`;
- all tests pass with zero failures or errors and only documented skips;
- all 11 `verifyLocal` tasks execute successfully;
- all three versioned artifacts are rebuilt;
- changed repository-relative documentation links resolve;
- roadmap and release text match completed Epic 007; and
- `git diff --check` passes.

## Publication procedure

1. Review and merge the `1.5.0` release checkpoint pull request.
2. Fast-forward local `main` to the exact merge commit.
3. Confirm merged `main` has the same tree as the validated preparation head.
4. Reuse validation only when those trees are identical; otherwise rerun it.
5. Create annotated tag `v1.5.0` with annotation
   `KAOS 1.5.0 - First Tool Integration` at verified merged `main`.
6. Push only the `v1.5.0` tag.
7. Create the GitHub Release from that tag using the reviewed release notes.
8. Upload `KAOS-1.5.0.jar`, `KAOS-1.5.0.tar`, and `KAOS-1.5.0.zip`.
9. Verify local and remote tag targets, annotation, release assets and hashes,
   release metadata, Epic/Project state, milestone closure, branch cleanup, and
   clean synchronized `main`.

## Limitations and next checkpoint

This version identifies the complete First Tool Integration baseline; it does
not claim unrestricted files, binary parsing, tool chaining, automatic action,
remote providers, a general tool framework, production readiness, or permanent
API compatibility.

Completed Epics 000–007 become immutable release evidence. The next epic must
be analyzed before it is activated.
